# SQLite scaling investigation

The corrected load driver passes correctness at 50, 100 and 250 seats, but misses
the 100 ms stream target. See [the baseline runs](results-2026-10-08.md).
The metric is request-start-to-stream arrival, an upper bound on commit-to-stream
latency. Throughput includes posting and draining each round; it is not saturated
write throughput.

## Profile at 100 seats

A private, measurement-only build captured CPU, mutex and block profiles after
setup, together with transaction durations and connection-pool counters. It used
Go 1.27.1; its timings are diagnostic, not the before/after comparison. The normal
comparison binaries use Go 1.26.8 and the same load driver.

Thirty message posts caused 20,016 read transactions and 1,514 write transactions,
including presence, acknowledgments and other bookkeeping. Beginning a write took
90 ms on average, while committing took 0.87 ms. No transaction returned
SQLITE_BUSY. That does not mean SQLite never waited internally.

The unbounded pool discarded 1,886 idle connections during the capture. Mutex
profiles point to query preparation and the driver's allocator, with repeated
full presence reads on stream wakes. The pinned driver's macOS allocator uses a
global lock; its Linux implementation differs. These findings do not establish
Linux or hosted-server performance. Profile wait totals aggregate goroutines and
must not be reported as elapsed time or server CPU usage.

## First candidate

Reuse four reader connections and give writes a separate, single-connection pool.
This bounds connection churn and prevents queued readers from occupying the
writer's slot. Reads keep their transaction snapshots; writes keep immediate
transactions, foreign-key checks, busy handling and current authorization checks.
There is no new cache, schema, API or permission rule.

A real SQLite test holds the only reader connection while a write commits. It
fails with the shared pool and passes with the separate writer. The SQLite race
contract suite and `make quick` pass. Independent source review found no blocker.

## Uninstrumented comparison

The matched 100-seat control completed 30 posts, 300 deliveries and ten verified
chains. Write response p50/p95/p99 was 46.8/122.3/152.5 ms; stream arrival was
283.2/398.7/427.1 ms. Long-poll wake was 156.7/306.4/324.7 ms and hand-over was
2501/2645/2706 ms. The round cadence was 1.20 posts/s.

The control's resource sampler failed to recognize the renamed binary, so CPU and
memory values are unavailable for that run. The sampler is corrected for the
candidate. Candidate measurements are pending; no performance gain is established.
