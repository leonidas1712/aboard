# Temporary Fly load results

These runs use a disposable Singapore (`sin`) Fly server: one `shared-cpu-1x`
machine, 512 MiB RAM and a 1 GiB volume. The initial images use main `e73e62a`;
later diagnostics and retries name their source versions below. All use Go 1.26.9
and the repository Dockerfile. The driver runs from a macOS laptop with private
homes and real delivery daemons, without models. No deployed team server is used.
No server settings were tuned between sizes.

## Driver correction

The first 500-seat attempt completed one round, then failed while preparing the
next round's observers. The driver required reuse of an idle socket; a proxy or
server closing that socket made preparation fail even though redial was safe.
It also verified 500 cursors serially. Its 642.5-second measurement therefore
includes cursor checks and failed observer preparation, not 642.5 seconds of
delivery latency. That attempt did not finish correctness or chain checks.

The corrected driver (#253) permits a new connection before posting and waits
for every observer request to be transmitted. Dials share a sixteen-slot limit.
After confirmed delivery, sixteen workers verify cursors. A measured observation
failure still fails the run; it is not hidden by an after-post retry. Reports now
include maximum latency and separate observer, delivery and verification times.
Both driver regressions failed first; focused races and `make quick` pass.

The next 500-seat attempt exposed a second driver boundary. It waited for every
stream observation, then processed harness frames in seat order. The slowest
stream observation arrived after 41.55 seconds, beyond the daemon's 30-second
harness reply window. Ready bundles could therefore expire before the driver
confirmed them. Durable state and logs showed retrying deliveries and fresh-inbox
deadline failures. That does not establish the cause of every slow stream read.

The follow-up (#254) confirms each extension independently after its own observer
read and exact marker, board and sequence validation. Delayed heads and an earlier
seat cannot gate another ready receipt. All stream, cursor and chain checks remain.
Two deterministic barriers failed first; package races, quick and source review pass.

## 250 seats

Twenty-five people, ten seats each, fifteen boards and twenty-five daemons completed
three rounds. All 45 posts, 750 deliveries and 15 hash chains verified. There was
no reset, loss, duplicate, ordering or cursor failure. Setup took 521.56 seconds
with eight throttled requests. Delivery measurement took 31.84 seconds, including
verification, or 1.41 paced posts/s. This is not concurrent write throughput.

| Milliseconds | p50 | p95 | p99 | Maximum |
| --- | ---: | ---: | ---: | ---: |
| Write response | 123.7 | 393.9 | 485.4 | 485.4 |
| Request to stream | 315.3 | 1029.4 | 1310.2 | 1420.5 |
| Request to long poll | 338.5 | 797.6 | 1030.9 | 1425.9 |
| Request to handover | 2924.4 | 4024.8 | 4617.4 | 5129.6 |

Each round's delivery phase took 4.54–5.64 seconds; cursor verification took
5.37–5.70 seconds. Observer preparation took 0.004–0.015 seconds. Sixteen concurrent
writers then posted and verified all 160 messages in 4.63 seconds: 34.58 posts/s,
sixteen writes in flight and no throttling. Their write p50/p95/p99 was
379.5/831.8/928.1 ms (maximum 950.4 ms). Read-back and audit are outside that timer.

There were 50 configured SSE connections and 250 long-poll observers; configured
connections are not a measured live-connection gauge. Stream p99 exceeded 100 ms,
so the tool exited nonzero despite completed correctness checks.

Persistent HTTPS `GET /v1/info` RTT, measured separately before delivery, was
8.4/12.5/14.6 ms p50/p95/p99 over thirty samples. Cold connections including TLS
were 39.8/51.1/55.2 ms. Both include Fly's proxy and lightweight server work.
Do not subtract these percentiles from delivery percentiles to infer server time.

## Interrupted 500-seat retry

The run used fifty people, ten seats each, twenty boards and fifty daemons. Setup
took 1058.83 seconds. It was stopped after 356.24 measurement seconds when progress
had stalled in the first delivery round. All 20 posts and 500 stream/poll observations
were recorded, but only 195 extension deliveries had been validated. No round,
concurrent-writer phase or chain audit completed. This is not a capacity or
correctness pass; the following partial measurements include the driver problem.

| Milliseconds | p50 | p95 | p99 | Maximum | Samples |
| --- | ---: | ---: | ---: | ---: | ---: |
| Write response | 145.8 | 728.7 | 1126.7 | 1126.7 | 20 |
| Request to stream | 405.0 | 1689.8 | 27194.6 | 41547.8 | 500 |
| Request to long poll | 493.0 | 1436.8 | 8665.4 | 15546.6 | 500 |
| Request to handover | 13336.8 | 82505.4 | 92621.5 | 92707.8 | 195 |

Handover samples exclude the remaining seats and include retries; they cannot be
compared as a completed distribution. Peak RSS was 116.87 MiB, with no memory crash.
Setup mean CPU was 9.8%; the stalled post-setup period averaged 8.4%, with brief
one-core peaks. CPU was not continuously saturated over that period.

Persistent HTTPS info RTT was 8.1/12.8/16.9 ms p50/p95/p99; cold connections were
37.8/46.6/51.0 ms. The app and volume were destroyed and app-not-found verified.
A new run with independent confirmations is needed before drawing capacity claims.

## Retry feedback follow-up

The interrupted run retained aggregate deadline categories and final journal state,
not the first retry's timestamp. It cannot establish whether the 41.55-second stream
outlier preceded or followed the first retries. That chronology is not claimed.

The daemon's failed handoffs use exponential backoff (1, 2, 4…60 seconds) and the
existing attempt/attention policy, but no jitter. A failed fresh inbox recheck before
handoff instead retries after `QueueGather` (two seconds), without exponential
backoff or jitter; each failed read can also consume its five-second timeout.
These paths can synchronize under overload. [Issue #255](https://github.com/leonidas1712/aboard/issues/255)
records this separate server/daemon follow-up. Neither path was tuned in the driver PRs.

## Resources and limits

The server's `/proc` CPU counters and RSS were sampled once per second. The 250-seat
run produced 568 samples. Setup mean interval CPU was 6.1%; after setup it was
75.4%, with a peak near one core. Peak RSS was 75.55 MiB. Phase boundaries use
elapsed time and samples can straddle them; after-setup samples include delivery,
writers, verification and audit. Brief CPU ratios above 100% reflect sampling
interval alignment, not an extra assigned core.

These are bounded single runs, not a saturation test. They include client scheduling,
network traffic, daemon gathering and server work. Local and hosted results use
different CPUs and operating systems. They do not isolate SQLite time or establish
an idle-stream timeout cause. The 512 MiB server did not run out of memory.

The temporary 250-seat app and attached volume were destroyed and an app-not-found
check confirmed teardown. Fly's CLI changed the `access_token` config field during
the run; only per-field hashes and changed field names were recorded, never values.
Raw load and resource artifacts remain private.

## Second confirmation boundary and server-wait diagnostic

A further 500-seat attempt used independent observer/seat confirmations but still
waited for every board POST response before enabling any receipt. It failed after
60.7 seconds with an empty long-poll result. Setup took 1,061 seconds; 20 posts,
469 poll observations and 252 deliveries were validated. No round, chain audit or
concurrent-writer phase completed. Stream samples were not collected before the
failure; their empty sample set does not mean zero latency.

| Partial sample | n | p50 ms | p95 ms | p99 ms | max ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Write response | 20 | 446 | 10,798 | 11,596 | 11,596 |
| Long-poll response | 469 | 3,695 | 20,050 | 24,156 | 30,560 |
| Validated handover | 252 | 34,179 | 56,888 | 57,973 | 58,877 |

After-setup CPU averaged 12.7% of one core and RSS peaked at 112.64 MiB. Persistent
HTTPS info RTT was 8.8/12.1/21.3 ms. Fresh inbox recheck deadlines first appeared
about 9.3 seconds after setup, before handoff failures at about 35.8 seconds. These
are approximate client/log phase alignments, not exact server transaction timings.
The partial delivery samples include retries and omit unfinished deliveries.

A held later POST reproduces the remaining driver barrier. Its repair releases each
board's validated receipt after that board's own successful immutable response;
a failed or uncertain POST authorizes none. Both checks are covered by deterministic
tests. This driver repair does not explain away server waiting: a private, write-heavy
50-seat Fly probe will measure volume fsync, iowait and reader/writer queue, body and
commit times before another full run. No production durability setting is changed.

The failed run's temporary app and volume were destroyed; an app-not-found check
confirmed teardown. It is not a successful 500-seat capacity result.

## Private write-heavy 50-seat diagnostic

Before another 500-seat attempt, a disposable one-shared-CPU, 512 MiB machine in
Singapore ran a privately instrumented build of main `7c9a8a3`. It retained the
production WAL durability settings. The workload used five people, ten seats each,
five boards, three delivery rounds and 16 concurrent writers posting 100 times each.
All 150 deliveries, five chains and 1,600 concurrent posts verified. The stream
latency target was missed, so the tool returned nonzero despite completed correctness
checks.

| Client metric | p50 ms | p95 ms | p99 ms | max ms |
| --- | ---: | ---: | ---: | ---: |
| Round write response (15) | 54.8 | 215.8 | 215.8 | 215.8 |
| Request-to-stream (75) | 101.0 | 309.0 | 367.2 | 367.2 |
| Long-poll response (150) | 135.3 | 253.6 | 280.9 | 286.7 |
| Handover (150) | 2,302.0 | 2,549.8 | 2,721.6 | 2,771.5 |
| Concurrent write response (1,600) | 187.3 | 404.8 | 771.4 | 1,357.7 |

Concurrent throughput was 76.4 posts/s over 20.94 seconds, with no writer throttles.
The separate 200-iteration 4 KiB write-plus-fsync probe measured 0.416/0.672/0.963 ms
p50/p95/p99 and 1.246 ms maximum. Cold HTTPS info RTT was 40.3/52.7/63.8 ms; a
persistent-connection baseline was not captured in this diagnostic.

The busiest ten-second timing interval contained 1,170 ordinary writer transactions:

| Private server timing | mean ms | p95 ms | p99 ms | max ms |
| --- | ---: | ---: | ---: | ---: |
| Writer pool queue | 30.86 | 230.26 | 453.03 | 939.60 |
| Writer transaction body | 1.41 | 3.30 | 4.56 | 61.06 |
| Commit | 0.67 | 1.43 | 3.72 | 68.67 |
| Reader pool queue | 0.0012 | 0.0023 | 0.0039 | 0.28 |

These are interval distributions, not whole-run percentiles; adding their percentiles
does not yield an operation percentile or a service-capacity estimate. The probes
record pool acquisition, begin, body and commit separately, without SQL, credentials
or payloads. Expected read refusals were counted as body errors, not classified as
SQLite lock failures. Instrumentation was private and never shipped.

A quoting error lost early resource samples. The corrected sampler retained 37
samples after setup: mean CPU 34.7% of one core, peak 91.9%, mean iowait 0.33%,
maximum iowait 3%, and peak RSS 48.62 MiB. Coverage includes writers and verification;
it does not support a whole-run resource average.

At this size the dominant measured write delay is pool queueing, not fsync. This
bounded probe does not reproduce or identify the complete 500-seat stall. The next
step is to count writer transactions by operation in an isolated local 500-seat
workload, including idempotency receipts, presence, acknowledgements and queue
reports, before another hosted run. No `synchronous=NORMAL` experiment was warranted.
The temporary diagnostic app and volume were destroyed, and an app-not-found check
confirmed teardown. Fly refreshed only its `access_token` configuration field.

## 500 seats after bookkeeping reduction

One final run used main `880e472`, including #259 and the pending-post confirmation
fix, on one shared CPU, 512 MiB, Singapore and one volume. It used 50 people,
10 seats each, 20 boards and 50 real daemons. WAL durability and production rate
limits were unchanged. This compares different revisions and driver fixes; it is
not an isolated causal benchmark for #259.

Round one completed 20 posts, all 500 deliveries, all 500 long-poll observations,
500 stream observations and every expected cursor check. Round two failed while
opening its observer connections: a TLS handshake exceeded its ten-second timeout.
The overall run is **incomplete**: three rounds, chain audit and the 16-writer phase
were not reached. No concurrent-writer throughput is claimed.

| First-round metric | p50 ms | p95 ms | p99 ms | max ms |
| --- | ---: | ---: | ---: | ---: |
| Write response (20) | 95.7 | 702.6 | 1,192.9 | 1,192.9 |
| Request-to-stream (500) | 548.1 | 1,378.2 | 2,202.9 | 2,571.2 |
| Long-poll response (500) | 552.8 | 1,522.6 | 2,781.0 | 3,073.0 |
| Handover (500) | 3,979.6 | 16,053.1 | 34,799.1 | 63,319.6 |

Write p95 fell from the previous incomplete 500-seat run's 10,798.5 ms to 702.6 ms,
about fifteenfold. The handover tail remains slow. Setup took 1,059.01 seconds;
measurement ran 293.84 seconds before the observer failure. First-round delivery
and observer collection took 68.13 seconds, followed by 215.63 seconds of cursor
verification. The tool's 0.068 posts/s aggregate includes those waits and is not
server write throughput.

The aggregate counter records 16 HTTP 429 retries. Source and setup order attribute
these to provisioning `POST /v1/join`, capped at 30 per minute per client address:
500 sequential joins need sixteen pauses, while connects arrive only once per ten
joins. Message POSTs and inbox GETs have no such limiter. The retained counter does
not store request paths or phases, so this route attribution is an inference, not
captured per-request evidence. Future test-server setup should retain that split.

Persistent HTTPS info RTT, measured separately, was 7.83/10.03/18.80 ms p50/p95/p99.
Cold TLS/proxy info RTT was 39.22/45.82/79.70 ms. Neither is an exact server-only
latency measurement, and subtracting independent percentiles is invalid.

The resource sampler retained 1,310 points through setup and measurement. After
setup it retained 256 points: sampled mean CPU 10.33%, time-weighted CPU 9.95%,
peak CPU 99%, and peak RSS 105.23 MiB. Sampled mean iowait was 1.94%, time-weighted
mean 1.98%, with a 20.83% peak. The weighted window covers 299.20 seconds and
includes shutdown activity around the incomplete measurement; the largest sample
gap was 1.44 seconds. These are guest samples, not a CPU-capacity proof.

The first inbox recheck deadline error occurred approximately 13.71 seconds after
setup; 74 such errors and one later inbox-read deadline error were captured. The
maximum stream latency was 2.57 seconds relative to its own POST, while errors are
timed from setup completion. Per-POST start timestamps are not retained, so these
different clocks cannot establish whether that maximum preceded the first recheck.
No failed-handover retry was recorded. #255 tracks jitter/backoff for these daemon rechecks separately.

The temporary app `aboard-load-500-a1460d46` and attached volume
`vol_v3gkon8165znlmw4` were destroyed. A separate Fly app inventory confirmed the
app was absent; Fly's status command also reported that it could not find the app.
Only the `access_token` field changed in the real Fly configuration during routine
refresh; field values were never printed.

No more Fly 500 runs are planned in this time-box. The completed 250-seat run is the
current evidence for a one-shared-CPU team server. Round-one delivery at 500 is
proven, but steady-state 500-seat correctness and performance remain unverified;
use a larger machine beyond the demonstrated range pending further measurement.
