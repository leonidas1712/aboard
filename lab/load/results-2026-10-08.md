# Local load proof, 2026-10-08

The target is 50 people with ten agent seats each across 20 boards. Each person has
an isolated home and a real delivery daemon; fake extensions confirm hand-overs.
No model calls or existing credentials are used. The server binds a private ephemeral
loopback address, never the installed server's port. The machine has an arm64 CPU,
ten logical CPUs and 32 GiB memory.

## Baseline connection failure

`make load` on `0c2f8e9` provisioned all 50 people, 500 seats, 20 boards and 50 daemons
in 1,038.48 seconds, with 16 throttled requests. At the start of the first measured
round, an observer TCP connection was reset before HTTP transmission. The measurement
phase lasted 33 ms and posted no messages. Latency, throughput and correctness results
are unavailable; zero samples must not be presented as zero latency.

Before cleanup, the server and all 50 daemons were still running. Their diagnostics
recorded no warnings, errors, panics, SQLite lock errors or open-file exhaustion.
The inherited file-descriptor limit was 1,048,575. Passive one-second process snapshots
recorded peak server RSS of 213.33 MiB and peak CPU of 444.7% (about 4.45 cores).
Median sampled CPU over provisioning was 1.9%. These are process snapshots, not an
average CPU cost per message. Documentation builds and screenshot work overlapped the
start of this run, so these resource snapshots are not an isolated baseline. System
TCP statistics exposed no usable counter changes.

The driver attempted 500 observer connections concurrently. A separate loopback
TCP probe, with no aboard handlers or SQLite, reproduced 20 connect resets in 5,000
dials at concurrency 500. At concurrency 16, all 5,000 succeeded. The host listen
backlog was 128. This supports connection-burst pressure as the explanation; it does
not identify the precise kernel queue that dropped the original connection.

The driver repair at `94bc3e9` limits simultaneous connection establishment to 16.
It does not limit active requests: all 500 observers must still be transmitted before
the first measured post. It adds no retry for failed observations and changes no
server setting, rate limit or SQL behavior. Successful write-response timings are
now retained even if a later stage fails.

## Second full run and pending repair

The second full run on `94bc3e9` also failed before its first measured post.
Provisioning took 1,029.76 seconds with 16 throttled requests. All 500 seats and
50 daemons were ready, but an observer connect was reset after 28 ms of measurement.
All 51 child processes were still running, with no diagnostic warnings or errors.
Peak sampled server RSS was 181.22 MiB; peak CPU was 483.7%, and median provisioning
CPU was 1.8%. There are still no write, delivery or throughput samples.

Limiting concurrent dials alone did not fix the full workload. The next driver change
serially primes dedicated observer connections with authenticated `/v1/me` responses,
then requires the concurrent polls to reuse those connections. A bounded test verifies
64 requests all remain open together on reused connections; the real-server smoke
and load package pass with the race detector. The size ladder below is measured on `e7ba20c`; its runtime is identical to the
priming candidate used for the first size. A full 500-seat run remains pending.
This is a test-driver repair, not a server tuning result.

The first size verified all five chains and every delivery, with no lost, duplicate
or out-of-order messages. Setup took 61.77 seconds; measurement took 12.60 seconds.
Request-to-stream p99 was 208.27 ms, so the conservative 100 ms target was not met.

and measurement; CPU peaks describe one-second snapshots and can exceed 100% across
multiple cores. Median sampled CPU was 0.0% across the join-limited provisioning run.

33.66 seconds. Request-to-stream p99 was 444.58 ms, missing the conservative target.
Median sampled CPU was 0.0%. Neither throughput figure is a write-capacity benchmark:
the driver posts sequentially, drains each round and verifies each seat's server ack
serially. The configured streams and warm observers do not prove cold-connection capacity.

## Incomplete 250-seat round

The 25-person / 250-seat / 15-board run provisioned in 502.38 seconds, with eight
throttled requests and 50 configured SSE streams. It posted 15 messages and recorded
250 stream and long-poll observations, without the earlier TCP connect reset.

The driver then stalled during confirmation: it waited for each seat's server ack
before confirming the next fake extension. The production harness call window is
30 seconds; 210 seats were acknowledged, while the remaining 40 delivery records
were in retry with `harness_error`. Their daemon diagnostics recorded 40 timeouts.
The driver observed 211 handovers before the stalled ack. No chain verification ran.

Only the owned fixture server was stopped to return partial counters. The subsequent
connection-refused error was induced by this diagnostic stop, not an observed server
crash. The 459.72-second measurement duration includes the stall; its posts-per-second
value is not a throughput result. These incomplete first-round latency distributions
are diagnostics, not a correctness or performance pass:

| Metric | Samples | p50 ms | p95 ms | p99 ms |
| --- | --- | --- | --- | --- |
| Write response | 15 | 87.15 | 325.79 | 325.79 |
| Request-to-stream | 250 | 593.04 | 861.92 | 956.71 |
| Long poll | 250 | 268.40 | 570.09 | 651.35 |
| Handover | 211 | 3039.73 | 3366.95 | 3559.21 |

Peak sampled server RSS was 194.13 MiB, peak CPU 443.5%, and median CPU 12.3% across
914 snapshots including the stalled interval. The next driver change confirms every
fake extension before beginning server ack verification. A bounded acknowledgment
barrier test fails under the old ordering; all existing correctness checks remain.
A corrected 250-seat rerun is pending. No SQLite tuning has been made.

## Idle SSE keep-alive

Current source and the `v0.1.2` tag already emit and flush `: keepalive` comments every
25 seconds. The public API contract specifies the interval. Both browser and daemon
silence watchdogs count comments as activity. The focused
`TestStreamSendsAKeepaliveEvery25Seconds` race test passes.

The reported idle drops on the deployed team server remain unmeasured. The investigation
is parked pending a connection trace and drop interval; adding another heartbeat would
duplicate existing behavior. No Fly deployment or configuration change was made.
