# Local 500-agent load result

The current-main server (`5201007`, Go 1.26.9, macOS arm64) completed the default
topology: fifty people, ten agent seats each, twenty boards and fifty real delivery
daemons. It used private homes/state, an ephemeral loopback listener and no models.
The load tool from #239 ran three delivery rounds followed by sixteen concurrent
writers posting ten messages each. No server settings or limits were changed.

## Delivery ladder

| Milliseconds, p50 / p95 / p99 | Final 250 seats (#242) | 500 seats (current main) |
| --- | --- | --- |
| Write response | 39.8 / 157.7 / 236.9 | 67.6 / 213.2 / 347.6 |
| Request to stream | 114.2 / 267.2 / 312.0 | 202.7 / 531.5 / 653.1 |
| Request to long poll | 83.8 / 237.4 / 282.1 | 145.0 / 446.4 / 605.4 |
| Request to handover | 2188 / 2328 / 2408 | 2358 / 2690 / 2815 |
| Peak server RSS | 82.36 MiB | 133.72 MiB |

All sixty delivery posts, 1,500 deliveries and twenty chains verified. No observer
connection reset, missing delivery, duplicate, ordering failure or cursor failure
occurred. Setup took 985.08 seconds with sixteen throttled setup requests. The
delivery measurement took 43.86 seconds, or 1.37 paced posts/s. This cadence includes
fan-out draining and gathering; it is not concurrent write throughput.

The run reported `status: complete`, but `make load` exited nonzero solely because
stream p99 exceeded the 100 ms conservative target. Correctness passed; the latency
target did not. Request-start measurements include client/server scheduling and
loopback traffic, not exact database commit timestamps.

The configured SSE count was 100 (person and daemon streams); it is not an observed
live connection gauge. Five hundred independent long-poll observers were established
before each measured round. The daemon connections also generate their own traffic.

The [250-seat result](../../engineering/read-stampede.md) used Go 1.26.8 and preceded
the queued/mid-turn delivery changes. These single local runs show the observed
workloads, not a controlled isolation of seat count or hosted performance.

## Concurrent writers

Sixteen distinct provisioned agents started together. All 160 posts were read back
and verified, with a peak of sixteen writes in flight and no throttling. The post-only
phase took 1.977 seconds, or 80.94 successful posts/s. Write-response p50 / p95 / p99
was 134.1 / 359.1 / 535.7 ms. Read-back verification and final chain verification are
outside that throughput timer. This is a bounded workload, not saturated capacity.

## Server resources over time

The owned server's RSS and cumulative CPU time were sampled once per second through
the run: 1,036 samples, zero sampling errors. Interval CPU can exceed 100% across
cores. Phase labels are taken when sampled; intervals can cross a phase boundary.

| Sample phase | Samples | Mean interval CPU | Peak interval CPU | Peak RSS |
| --- | ---: | ---: | ---: | ---: |
| Setup | 986 | 9.1% | 338.7% | 84.86 MiB |
| Delivery | 43 | 100.6% | 296.2% | 133.72 MiB |
| Confirmation | 3 | 312.0% | 362.7% | 124.11 MiB |
| Concurrent writers | 3 | 297.4% | 344.2% | 121.67 MiB |
| Audit | 1 | 95.8% | 95.8% | 121.94 MiB |

Short phases have few samples; these are approximate resource observations, not
precise phase CPU attribution. The previous 250-seat monitor used `ps`'s moving CPU
estimate, so its CPU peak is not compared with these interval samples.

Raw JSON and resource samples remain in private proof artifacts. No cloud resource
was created for this result. The temporary Fly run and separate network round-trip
measurement are approved and remain pending execution with 512 MiB RAM. Further server tuning is a
separate change; this run made none.
